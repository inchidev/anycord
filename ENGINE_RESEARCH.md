# Anycord engine integration research

Evidence checked: **2026-10-14**. Scope: static Nuxt frontend; no deployed Nitro server; one selected backend per installation; Better Auth remains the identity/session owner. No engine was provisioned, upgraded, or deployed by this research.

## Recommendation and proof boundary

Keep the frontend HTTP/event contract independent of a runtime, SQL driver, native backend SDK, or authentication token format. celld and Cloudflare can share the Worker implementation. TrailBase can host our API inside a WASM component and is a plausible target for embedded Better Auth, subject to a real runtime spike. PocketBase can host our API in Go or JavaScript hooks, but its stock JavaScript environment is not a supported runtime for the existing Better Auth server. For PocketBase, the practical Better Auth-preserving option is a small private auth service plus engine-native routes; a custom embedded modern JS runtime is a separate, substantially larger integration project. Neither requires Nitro. These are architectural conclusions from the sources below, **not proof that all four adapters run**.

| Engine | Deployment boundary | Anycord API router | Better Auth path | Evidence/proof today |
| --- | --- | --- | --- | --- |
| celld | Self-hosted/VPS Worker-compatible runtime | Existing `worker/index.ts` | Existing Worker configuration with D1 Drizzle adapter | Source is implemented locally; this research did not rerun its integration tests |
| Cloudflare | Managed Cloudflare Workers, D1, Durable Objects; this target does not run as a VPS package | Same Worker family | Worker-compatible Better Auth with D1 | Reusable source/configuration, not a provisioned or live-tested Cloudflare installation |
| TrailBase | Self-hosted native server + compiled WASM component | TypeScript WASM handlers, or a custom Rust/axum binary | Investigate embedding in the WASM guest first; private auth service is fallback | Official extension mechanism confirmed; Anycord API/auth embedding unimplemented/unproven |
| PocketBase | Self-hosted Go binary, optionally with `pb_hooks` | Prefer custom Go routes for Anycord; synchronous hooks are available | Private Node/Bun auth service; custom modern JS embedding only after explicit design decision | Official custom routes confirmed; Anycord auth bridge unimplemented/unproven |

The celld/Cloudflare distinction is a deployment/runtime choice, not a promise that Cloudflare-managed resources can be started on a VPS. Existing local evidence: `worker/index.ts`, `worker/better-auth.ts`, `wrangler.jsonc`, `scripts/build-worker.mjs`, and `package.json`.

## TrailBase: custom API can be embedded; Better Auth needs a spike

TrailBase loads `.wasm` components from `<traildepot>/wasm`. Its supported TS template bundles JS, then uses `jco componentize` against `trailbase-wasm` WIT interfaces. It registers routes with `defineConfig({ httpHandlers: [...] })`. There is also a native Rust router extension, with an explicitly unstable Rust API. [Custom API documentation](https://trailbase.io/documentation/apis_js/), [extension options](https://trailbase.io/documentation/apis_overview/), [pinned TS build template](https://github.com/trailbaseio/trailbase/blob/v0.34.5/examples/wasm-guest-ts/package.json).

The guest handler receives TrailBase's `HttpRequest`, not a browser `Request`: headers are byte tuples; body and JSON accessors are synchronous; `user()` supplies **TrailBase-native** identity. Responses use `HttpResponse` or WASI responses. A small HTTP bridge must construct a standard Request for Better Auth and convert status/body/headers back, preserving every `Set-Cookie` separately. Never treat `req.user()` as a Better Auth identity automatically. [Pinned request type](https://github.com/trailbaseio/trailbase/blob/v0.34.5/guests/typescript/src/http/request.ts), [pinned response type](https://github.com/trailbaseio/trailbase/blob/v0.34.5/guests/typescript/src/http/response.ts).

Current ComponentizeJS documents `Request`, `Response`, `Headers`, `fetch`, WebCrypto, and resolving exported async functions through its event loop. Thus “TrailBase WASM cannot run async JS or has no crypto” would be incorrect. These advertised APIs make embedding plausible; exact WebCrypto algorithms, Request/cookie behavior and compiler compatibility remain runtime checks. Cryptographic randomness must remain enabled; ComponentizeJS documents deterministic values when its random feature is disabled. [ComponentizeJS platform APIs, async support and feature controls](https://github.com/bytecodealliance/ComponentizeJS#platform-apis).

The existing `drizzle-orm/d1` adapter cannot be carried over unchanged: TrailBase is not D1. The guest exposes parameterized `query`/`execute` and a transaction resource. Build a Better Auth custom database adapter over these APIs, or prove an appropriate SQL-driver bridge; do not pass the TrailBase browser SDK as `database`. Validate date/boolean/null conversion, uniqueness errors, filtered update/delete semantics, pagination and transaction behavior. Better Auth publishes a custom adapter factory and adapter tests. [Pinned TrailBase SQL API](https://github.com/trailbaseio/trailbase/blob/v0.34.5/guests/typescript/src/db/index.ts), [Better Auth adapter guide](https://better-auth.com/docs/guides/create-a-db-adapter).

Better Auth 1.7.7 installed source uses `@better-auth/core/async_hooks` in request/endpoint/transaction context. Its normal branch imports `node:async_hooks`; its `edge` branch has a pure-JS fallback explicitly intended for short-lived single-threaded serverless functions. TrailBase's documented per-request WASM isolation makes testing that branch reasonable, but request isolation and nested async behavior must be proved; a mutable global substitute in a shared runtime is unsafe. Select package export conditions deliberately and inspect the bundle for remaining `node:*` dependencies. Local evidence: `node_modules/@better-auth/core/package.json`, `dist/async_hooks/{index,pure.index}.mjs`, and `dist/context/*`. [Upstream async-hooks implementation](https://github.com/better-auth/better-auth/blob/main/packages/core/src/async_hooks/index.ts), [TrailBase runtime/isolation explanation](https://github.com/trailbaseio/trailbase/blob/v0.34.5/docs/src/content/blog/switching_to_a_wasm_runtime.mdx).

Passwords add a practical performance question. Installed Better Auth delegates to `@better-auth/utils/password`; Node uses `node:crypto` scrypt, while the other implementation uses asynchronous pure-JS scrypt and secure random bytes. Anycord already chooses that JS implementation for celld because its native scrypt is unavailable. A TrailBase bundle should deliberately use a compatible path and benchmark its CPU/memory behavior under parallel login attempts; do not weaken hash parameters to make the demo pass. Local evidence: `scripts/build-worker.mjs`, `node_modules/better-auth/dist/crypto/password.mjs`, `node_modules/@better-auth/utils/dist/password{,.node}.mjs`.

## PocketBase: embed routes, preserve Better Auth in a compatible runtime

PocketBase exposes custom Go routing through `app.OnServe()` and can register middleware, groups and catch-all patterns. Its prebuilt binary also supports `routerAdd(...)` hooks. Go gives direct access to request/response objects and is the clearest place for session-validation middleware and live-connection handling. Use application-specific routes and check collisions with PocketBase's system `/api` routes. [Go routing](https://pocketbase.io/docs/go-routing/), [JS routing](https://pocketbase.io/docs/js-routing/).

The stock JS hook VM uses Goja; it is neither Node nor a browser. Its docs describe CJS module loading, serialized handler scope and no concurrent execution within a handler. It does not provide the supported async Web Request/Response + WebCrypto + AsyncLocalStorage environment expected by the current Better Auth server. Bundling ESM into CJS only addresses module syntax; it does not supply those host APIs or an async HTTP handler lifecycle. Do not infer “npm install better-auth” enables server-side auth in `pb_hooks`. [PocketBase runtime limitations](https://pocketbase.io/docs/js-overview/).

Avoid the broader outdated claim that Goja itself has no Promise support: current [Goja source includes Promise support](https://github.com/dop251/goja/blob/master/builtin_promise.go). Its maintainers explicitly distinguish the language engine from a host-provided event loop and say a runtime cannot be used concurrently from multiple goroutines. The blocker is the complete PocketBase host integration required by Better Auth, rather than one JS keyword. [Goja host/event-loop requirements](https://github.com/dop251/goja#where-is-settimeoutsetinterval), [Goja concurrency requirements](https://github.com/dop251/goja#is-it-goroutine-safe).

Practical design: run Better Auth in a minimal private Node/Bun process on the same installation, route `/api/auth/*` to it at the public origin, and keep application routes in PocketBase. Auth stores its own tables in a dedicated auth SQLite DB, or uses a tested adapter to private PocketBase operations. Do not have a separate ORM casually alter PocketBase-managed collection schemas or rely on two processes' migration assumptions. Better Auth supports SQLite and custom adapters without Nuxt or Nitro. The alternative, a custom Go binary embedding a modern JS runtime with WebCrypto and async support, is feasible in principle but has a much larger maintenance surface and was not validated here. [Better Auth installation/SQLite](https://better-auth.com/docs/installation), [Better Auth Web Request handler](https://better-auth.com/docs/integrations/hono).

A private auth service keeps Better Auth authoritative. PocketBase `RequireAuth()` validates PocketBase auth records, so it must not be used as if it validated a Better Auth cookie. Implement middleware that validates the actual Better Auth session through a private authenticated service call, or a carefully specified session-verification bridge with logout/revocation semantics. Never trust a browser-provided `X-User-Id`. [PocketBase request auth state and middleware](https://pocketbase.io/docs/go-routing/).

## Shared identity, authorization and realtime requirements

These are proposed Anycord integration requirements, derived from the current API behavior; they are not claims that TrailBase or PocketBase enforces them automatically.

1. One public origin serves static Nuxt assets and `/api`. The selected backend/reverse proxy sends auth paths to the compatible auth runtime when necessary. Keep cookies HttpOnly, use Secure with HTTPS, preserve SameSite/CSRF checks and canonical `AUTH_BASE_URL`/trusted origins. A proxy must preserve multiple cookie headers and reject forged forwarding/identity headers. [Better Auth cookie model](https://better-auth.com/docs/concepts/cookies).
2. Better Auth owns account IDs and session validity. Engine profiles map to that stable identity; backend-native IDs remain internal or have an explicit mapping. No silent switch to native engine auth; no independent password database or implicit account linking by username/email.
3. Every workspace/channel/message/search/settings route checks the authenticated identity and current membership. A valid session proves identity, not membership or admin rights. Native record APIs stay private/locked unless they apply equivalent authorization. TrailBase's `_USER_` and PocketBase's `Auth` are native concepts; our Better Auth identity is not automatically injected into them. [TrailBase record access rules](https://trailbase.io/documentation/apis_record/), [PocketBase Go request auth](https://pocketbase.io/docs/go-routing/).
4. Keep event payloads separate from transport. PocketBase offers custom broker messages; TrailBase offers native record subscriptions. Neither alone proves Anycord typing, presence, authorization, logout disconnect and member-removal behavior. Do not expose native subscriptions with broader access than HTTP reads. A transport bridge must revalidate membership and close/reject revoked sessions; account for multiple tabs and reconnect. [PocketBase custom realtime broker](https://pocketbase.io/docs/go-realtime/), [TrailBase subscriptions](https://trailbase.io/documentation/apis_record/#subscribe).
5. Keep mutation ordering explicit: persist first, then publish; a notification failure must not pretend the stored write failed. The existing Worker already uses this behavior. History queries provide recovery after reconnect; no guarantee of durable event replay should be advertised without implementing it.

## Next validation spike

First implement a disposable **TrailBase 0.34.5** fixture, without existing application data. Pin `trailbase-wasm`, jco and ComponentizeJS. Build and run a tiny WASM route that verifies standard Request/Response/Headers, multiple Set-Cookie headers, cryptographic randomness, SHA/HMAC, promises, timers and SQL parameter binding. Then bundle Better Auth **1.7.7** with the deliberate edge/pure-JS password choices, a minimal custom SQL adapter and no unexpected Node imports. Verify signup, username login, get-session, logout and restart persistence. Include two concurrent accounts to detect identity/context leakage and record scrypt latency/memory before choosing the integration.

Next use a **PocketBase 0.40.5** disposable fixture with one private Better Auth service and one Go route. Prove auth-cookie forwarding, a rejected spoofed identity header, private session validation, exact identity-to-profile mapping, cross-workspace denial and logout/revocation. After that, add one message write plus event delivery/reconnect and member-removal checks. Run Better Auth adapter tests if storing its tables through a custom engine adapter.

**Decision remaining:** if the deployment requirement is “one process/binary with Better Auth on every engine,” stock PocketBase cannot satisfy it through its documented JS hooks; choose a custom embedded runtime project or relax the one-process requirement. If “no Nitro” means no Nitro application server, the small private auth service is compatible and the common frontend contract can proceed now. Do not silently replace Better Auth to hide this tradeoff.
