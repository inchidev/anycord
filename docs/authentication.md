# Authentication and Telegram

An Anycord installation owns its accounts and sessions. A server/community is a membership boundary inside that installation. Telegram and username/password users can belong to the same server. Linking Telegram adds a way to access an existing account; it does not copy messages, merge accounts or join additional servers. Independent installations retain independent identities.

## Installation owner

Open **User Settings → Installation Settings → Authentication** to enable username/password, Telegram browser login and Mini App auto-login, and to allow or close registration. These settings affect every server hosted on the installation. A community owner who is not the installation owner cannot change them.

The first owner still uses the existing password/setup-code bootstrap. Telegram cannot bypass first-owner setup. Closing registration blocks new accounts through all enabled methods while existing users can still sign in and explicitly link Telegram. Password login cannot be disabled until the owner's linked Telegram account has completed browser OIDC login. OIDC credentials can be changed only while password login is enabled; changing them requires another successful browser login before password login can be disabled again. Existing sessions are retained when a login method is disabled.

## Configure a Telegram bot

1. Create or select a dedicated bot in [BotFather](https://t.me/BotFather). In **Installation Settings → Integrations → Telegram**, paste the bot token and save. Anycord verifies it with `getMe` and shows the bot username.
2. In BotFather's Web Login / Login Widget settings, enable the new OIDC flow and copy its **Client ID and Client Secret**. The Client Secret is a separate credential; the bot token does not replace it.
3. Register the installation's public HTTPS origin and the exact callback URL shown in Settings. The callback is `https://YOUR_HOST/api/auth/callback/telegram`. Client ID and bot token must belong to the same bot. Keep the default RS256 signing algorithm; the `profile` scope is required to obtain the Bot API user ID.
4. Save the OIDC credentials and enable Telegram browser login in Authentication. Test “Continue with Telegram” in a separate browser session, then link your own existing account from **User Settings → Telegram**.
5. Set the bot's Main Mini App or menu-button Web App URL to the displayed `https://YOUR_HOST/login`. Enable Mini App login in Authentication. Launch it in Telegram: signed launch data is exchanged for an ordinary Better Auth session. An already signed-in account is never silently replaced; use User Settings to link it explicitly.

Use separate test credentials and a public HTTPS tunnel for local Telegram testing. Set the test installation's `AUTH_BASE_URL` to the tunnel origin and register its origin/callback in BotFather. A changed tunnel URL needs updated configuration. Keep production and test bots separate.

Saved bot tokens, OIDC secrets and webhook verification secrets are encrypted with the installation's `APP_SECRET`. Blank secret fields retain the saved value. “Remove bot” disables Mini App login and delivery, removes personal bot consent/preferences and pending notifications; the OIDC credential fields remain independently configurable. Clear the Client ID to disable browser OIDC. Preserve `APP_SECRET` in installation backups.

## Personal notifications

1. The owner enables Telegram notifications in Integrations, saves, then selects **Connect notification webhook**. This calls Telegram `setWebhook` with a random secret and the installation's `/api/telegram/webhook` URL. It replaces any existing webhook on this bot: use a dedicated bot.
2. A member links Telegram in **User Settings → Telegram**, opens the configured bot and presses **Start**. Return to Settings and refresh bot access. Starting the bot before linking does not authorize a later account automatically; start it again after linking.
3. Enable Telegram notifications and save. Message previews are off by default. Use **Send test notification** to check delivery. Login never requires notification consent or phone-number access.
4. Delivery covers explicit `@username` text mentions, replies to your messages and new messages in threads you explicitly follow using the thread's bell button. Mute channels in User Settings. Unfollow via the bell button. Telegram-created accounts display their normal name. Their unique internal mention handle remains unchanged; replies and followed threads avoid having to type that handle.
5. Disable notifications, send `/stop` to the bot, block it or unlink Telegram to stop delivery. Unlinking requires another usable password login. Telegram-created accounts can add a username/password in User Settings without creating a second user or losing history; adding a password requires a recent session.

Messages are queued only after a new message is saved. The outbox deduplicates message/recipient pairs, rechecks current preferences and membership before sending, and uses bounded retries for definite Telegram rejection. A network timeout or interrupted delivery is ambiguous and is not automatically resent, to avoid duplicate alerts. This is best-effort delivery, not an exactly-once guarantee. A sent alert cannot be withdrawn after access changes.

Cloudflare runs an additional once-per-minute scheduled handler for pending retries; existing daily attachment maintenance remains daily. Celld installations should invoke the Worker's scheduled handler every minute through their scheduler; new messages also flush pending delivery. Without scheduled invocations, retries wait for subsequent message activity. At most 10 queued notifications are attempted per flush and definitively rejected deliveries stop after three attempts. Completed records expire after seven days.

Telegram login uses the installation's own origin/cookies. A remote installation opened inside another Anycord client offers a link to open that installation directly; it does not transfer Telegram cookie sessions into another origin's bearer-token connection. Existing remote username/password connections continue to work while that method is enabled.

## Implementation and validation

Anycord pins Better Auth 1.7.7. The third-party [better-auth-telegram 2.0.1](https://github.com/vcode-sh/better-auth-telegram/blob/main/package.json) declares support for `>=1.6.22 <1.7.0`, so it is not installed with ignored peer requirements. A local Telegram plugin uses the supported Better Auth Generic OAuth implementation and a Mini App endpoint on the same internal account/session adapter.

Browser login uses authorization code + S256 PKCE, OAuth state, verified ID tokens and nonce binding. The adapter requires OIDC discovery verification and requests `openid profile`; there is no Telegram UserInfo endpoint. It maps the signed `id` claim to the same `telegram` provider/account key as Mini App `user.id`. Telegram's OIDC `sub` is a different identifier and is not used as a Bot API chat ID. Implicit account linking by email or name is disabled. Synthetic internal emails are never shown as real contact addresses. Verified OIDC `name`/`picture` and signed Mini App `first_name`/`last_name`/`photo_url` populate the Anycord display name and avatar. Names never display the legacy Telegram ID suffix. Internal unique handles, account IDs and password usernames remain unchanged. Explicitly linking Telegram to a password-created account preserves its chosen name while importing the avatar. Unlinking retains the imported profile image as the Anycord avatar; unavailable images fall back to initials.

HTTPS session cookies use `Secure; SameSite=None; Partitioned` so Telegram Web can maintain a session inside its iframe separately from the standalone browser session. Logout/refresh retain the same cookie attributes. HTML allows framing only by this installation and `https://web.telegram.org`; API responses retain frame denial. This policy applies both to Cloudflare static assets and celld's Worker-served shell; allowing a frame does not enable a disabled login method. Browser privacy policies may still restrict embedded cookies and must be checked on the target client.

Mini App login verifies raw `initData` HMAC-SHA-256 with the bot token, rejects duplicate fields and limits authentication data to five minutes with 30 seconds of future clock tolerance. Never trust `initDataUnsafe`. An existing Mini App session can refresh its profile through `/api/account/telegram/profile` with fresh signed launch data. The endpoint requires the signed Telegram ID to match the account already linked to that session, applies a rate limit and cannot create a session, link an identity or switch users. A failed profile refresh leaves the valid session usable. Callback URLs are restricted to local application destinations; BotFather also requires exact callback registration.

The client captures signed launch data before Nuxt's router initializes and keeps it only in that app instance. It removes Telegram launch parameters before routing, so nested query separators cannot be altered or carried into a login `next` URL. Mini App entry at `/`, `/login` (without an explicit destination), or `/main` opens `/servers`; explicit login destinations and channel deep links remain intact. Session resolution includes the single automatic Telegram sign-in attempt before showing any login form. An existing session consumes/skips this attempt, so explicit logout cannot silently sign back in; a failed/expired launch shows the normal form and an error without retrying on every route change.

The server picker and community menu offer **Join a server**. Paste a complete `/invite#token=…` link or its invitation code, check the destination community and installation, then explicitly join as the displayed account. This uses the current Mini App session. Expired/revoked/exhausted invitations and bans are enforced by the existing invitation API. Links from another installation are refused before their token is sent; switch installations and sign in there separately. Pending invitations survive login/reload in session storage, partitioned by installation, and are removed after acceptance or cancellation. A shared `/invite` link always selects the installation serving that link; `/join` uses the active connection.

Mini App entry at `/invite` preserves its invitation fragment through automatic sign-in. A Telegram `startapp=invite_<48-character-token>` entry also opens the confirmation screen on the bot’s installation. Invitation data selects a destination, never an identity or automatic membership. Existing password sessions remain active: link Telegram from that account’s User Settings to preserve history rather than creating a separate account.

User Settings and Installation Settings share one dialog with explicit account/installation scope and **Back to User Settings** navigation. The installation owner also has a direct entry from the picker and community menu; other members do not. Installation settings affect all communities on the displayed host. Server Settings remains scoped to its community. Close/Escape returns to the opening control; changing scope resets content/navigation scroll and focuses the scope heading. Closing or leaving installation administration unmounts credential fields.

Only Mini App launches load the [official Telegram Web App SDK](https://core.telegram.org/bots/webapps#initializing-mini-apps). Before loading it, Anycord removes signed identity from the fragment and passes only UI metadata, so the SDK cannot persist signed launch data. Its live `--tg-safe-area-inset-*`, `--tg-content-safe-area-inset-*` and viewport variables position the picker, chat, composer and teleported dialogs clear of device and Telegram controls. Browser `env(safe-area-inset-*)` remains the fallback; overlapping device values use the maximum, then Telegram's additional content inset is added. Only UI context and metadata are retained across reloads/PWA updates, so safe-area handling survives removal of the signed fragment without persisting or replaying identity. SDK load failure does not prevent server-side verified sign-in. The safe-area background and Telegram native header colour follow the active Anycord header in the picker, chat and settings. The Mini App flow, safe-area layout and profile/header polish were accepted on iOS using the isolated PR preview. Android acceptance remains separate.

`npm run test:telegram-launch` exercises the generated Nuxt client in Chromium with synthetic signed data: startup without a login-form flash, default picker routing and explicit deep links, single sign-in, existing sessions, verified profile refresh and explicit logout, normal names/provider avatars with initials fallback, header colour matching, expired launch fallback, disabled methods, first-owner setup, SDK failure, no signed URL/storage persistence, live top/side insets, dialogs and keyboard composer layout. It also checks invitation paste/preview/acceptance, foreign/expired/banned invitations, direct/startapp entry, remote-session isolation, membership refresh, owner-only settings entry, repeated scope navigation, close/Escape/focus and picker logout at mobile/desktop sizes. The browser matrix uses synthetic Telegram SDK/API responses. The same command also runs the built client against a disposable local Cloudflare Worker/D1 with actual Better Auth sessions and signed Mini App data: invitation preview, explicit acceptance, use count, private-community access, membership refresh and owner settings navigation. Only the Telegram SDK/provider is intercepted in that installation check. Real Telegram iOS/Android acceptance for this follow-up remains separate. It also checks ordinary browser login does not invent Telegram credentials. Install its test browser with `npx playwright install --only-shell chromium`; GitHub CI runs it after building. No real Telegram account or token is used by the browser regression test.

Run `npm run test:telegram` for a disposable workerd/D1 integration test with a local intercepted OIDC/JWKS/Bot API provider. No real Telegram credentials, messages or Cloudflare resources are used. It exercises actual Better Auth callbacks/cookies, identity convergence, linking, signature/claim failures, admission policy, setup/owner recovery, encrypted settings and notification authorization/deduplication/retry behavior. `npm run verify` includes this test and the existing application checks.

Before rollout, verify browser OIDC and real Telegram iOS/Android Mini App launch, cookie persistence, account linking, notification webhook delivery, block/unlink behavior and deep links using a dedicated test bot. Local provider tests do not establish native Telegram acceptance or production delivery.
